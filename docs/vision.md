# 渋谷共創ダッシュボード Vision

**文書の役割:** 製品の目的・対象者・到達目標の正本

## 1. 背景となる行政課題

渋谷区の行政課題「ダッシュボードの新規レポートの開発」より。

- 渋谷区は区の現状や課題を可視化する「SHIBUYA CITY DASHBOARD」を公開し、データに基づく
  施策検討を進めている。これまで庁内や事業者と連携してレポートを整備してきた。
- しかし、既存の指標・データに基づくレポートが中心で、**市民の多様なニーズや関心に応える
  新しい視点のレポートが不足**している。
- 可視化が一部の専門家向けで、**一般の区民にはまだ分かりにくい**。

### 要因

- ダッシュボードの設計が**行政内部の視点に偏っている**。
- 渋谷区は多様な人々が集まる都市であり、住民・来訪者・事業者の関心は多岐にわたる。
  行政だけでその全てを把握し、レポートとして設計し続けることはできない。

## 2. Vision

> **住民の声がダッシュボードになる。**
> 渋谷型「つくる → 公開 → 採用」サイクルで、多様な視点のダッシュボードを量産する。

渋谷区の住民・来訪者・事業者など多様な立場の人々が、ローカルニュースや AI との対話を
通じて自分の関心や課題を明確にし、コミュニティで議論・深掘りしながら解決方法を探る。
その過程を AI エージェント群が支援し、最終的に**「課題ごとの KPI 追跡ダッシュボード」**が
当事者の手で量産される。自治体はそれをピックアップして施策に反映し、施策がまたニュースとして
区民へ届く。

```text
ニュース配信 ─▶ 関心の醸成 ─▶ コミュニティ形成 ─▶ 課題の深掘り（課題カード）
     ▲                                                     │
     │                                                     ▼
 施策をニュースに ◀─ 施策検討（区が採用） ◀─ ダッシュボード ◀─ 仮説・検証（アンケート・データ収集・PoC）
```

ダッシュボードは「完成品のレポート」ではなく、**課題の当事者が仮説を立て、KPI で変化を
追い、行政と共に判断するための共有の場**である。

### System Purpose（正本）

> ニュースを起点に多様な区民・来訪者・事業者の関心を引き出し、AI 対話とコミュニティを通じて
> 根拠と KPI を持つ課題カードへ整理し、当事者が KPI 追跡ダッシュボードとして公開し、
> 区が採用判断して施策に反映する循環を支える。

System Purpose はこの1文だけを正本とし、[UX](ux.md)・[Feature](features.md) からは参照する。
probe-agent で実現することは実現方式であって System Purpose ではない（§9）。

## 3. Stakeholder と Need

| ID | Stakeholder | 抱えている課題（Problem） | 求めていること（Need） |
| --- | --- | --- | --- |
| STK-1 | 住民（例: 子育て世帯、高齢者、障がいのある人） | 日々の不満や困りごとを、行政に届く形にする手段がない | NEED-1 自分の困りごとが「課題」として認識され、改善が見えること |
| STK-2 | 来訪者（観光客・通勤通学者） | 区民でないため声を届ける窓口自体がない | NEED-2 一時的な滞在者の視点でも課題提起に参加できること |
| STK-3 | 事業者（店舗・企業・スタートアップ） | 地域課題と自社の取組みを結ぶ接点がない | NEED-3 課題解決への参加・実証の機会、データに基づく協働 |
| STK-4 | コミュニティ（町会・子育てサークル・NPO 等） | 議論はあっても根拠データや行政との接点が弱い | NEED-4 議論を根拠付きで整理し、行政へ提案できる形にすること |
| STK-5 | 渋谷区 各課の職員 | 区民ニーズを幅広く把握できず、ダッシュボード企画が内部視点に偏る | NEED-5 根拠と KPI を伴う区民発の課題を、施策検討の材料として受け取れること |
| STK-6 | オープンデータ提供者（区・都・国・民間） | データが公開されても使われ方が見えない | NEED-6 データが課題解決に使われ、整備の優先度が見えること |

**プロダクト上の扱い（MVP）**

| Stakeholder | プロダクト上の表現 |
| --- | --- |
| STK-1 / STK-2 / STK-3 | ロール「一般参加者」。住民・来訪者・事業者は登録時に選ぶ属性で、発言・課題カードに表示する |
| STK-4 | 機能上の単位「コミュニティ」。運営する人はロール「コミュニティ運営者」 |
| STK-5 | ロール「区職員」（担当課付き）。職員ビューと公式発言表示を持つ |
| STK-6 | 利用者ロールを持たない外部 stakeholder。価値の返却（データ利用状況の公開）は Later |

**価値交換（Value Exchange）**

- 住民・来訪者・事業者 → 区: 当事者の声、現場の観測、アンケート回答、ダッシュボード
- 区 → 住民・来訪者・事業者: 施策への反映、施策ニュース、公開データ、施策の効果（KPI の推移）
- コミュニティ ↔ 参加者: 議論の場、共感、仲間、課題の深掘り
- データ提供者 → 全員: オープンデータ ／ 全員 → データ提供者: 利用実績と整備ニーズ

## 4. Purpose Chain

| 要素 | 内容 |
| --- | --- |
| 対象者と現在の課題 | 多様な区民・来訪者・事業者の関心や困りごとが、行政のダッシュボードや施策に届いていない |
| 望ましい変化 | 当事者が自ら課題を言語化し、根拠と KPI 付きのダッシュボードとして公開し、区がそれを採用して施策に反映する循環が回る |
| システムの介入 | ニュースを起点に関心を引き出し、AI 対話・コミュニティ・データ整形を通じて「課題カード → KPI 追跡ダッシュボード」までの道のりを伴走する |
| 必要な能力 | 関心の収集、コミュニティ形成支援、課題カード作成、オープンデータ検索・整形、仮説検証支援、ダッシュボード生成、行政による採用と施策ニュース化（[Feature](features.md) 参照） |

## 5. Product Objective と Milestone

Objective は Vision へ近づくための中間目標、Milestone はその検証可能な到達点である。
数値目標はハッカソン段階の仮置きであり、実測前に達成を主張しない。

### OBJ-1 関心の顕在化 — ニュースから自分の課題に気づける

- 区のローカルニュースを読む流れの中で、関心や困りごとを AI との対話で言語化できる。
- **MS-1.1** 代表シナリオ（近所で外遊びできる場所）で、ニュース閲覧から関心の言語化、
  関連コミュニティへの誘導までを 1 人の利用者が完走できる。

### OBJ-2 コミュニティでの深掘り — 一人の不満を共有された課題にする

- 同じ関心を持つ人々がコミュニティで議論し、課題を可視化・深掘りできる。
- **MS-2.1** コミュニティのスレッドから、AI が根拠付きの「課題候補」を提示し、参加者が
  課題カード作成へ進める。

### OBJ-3 課題の構造化 — 区の注力分野と KPI に結びついた課題カード

- 課題が、渋谷区の 7 つの注力分野のどれに寄与するかと、追跡すべき KPI（最大 3 つ）を
  持つ「課題カード」として表現される。
- **MS-3.1** 課題カードが、対象者・場所/時間帯・根拠・注力分野・KPI を備え、根拠の出典へ
  遡れる状態で保存される。

### OBJ-4 仮説検証とダッシュボード化 — 当事者がデータで語れる

- 課題カードの KPI について、オープンデータ・アンケート・現場観測を集め、小さな施策を
  検証しながら KPI 追跡ダッシュボードとして公開できる。
- **MS-4.1** 代表シナリオで、KPI（例: 地域別の公園・児童遊園地の数、プレーパークの数、外遊び環境の満足度）を
  目標値と現在値付きで表示するダッシュボードが、当事者の操作で公開される。
- **MS-4.2** 専門知識のない利用者が、オープンデータの検索・整形を AI 支援で完了できる。

### OBJ-5 行政による採用と還流 — つくる → 公開 → 採用 のサイクルが閉じる

- 区の各課が公開ダッシュボードを閲覧・評価・ピックアップし、施策検討に反映する。
  施策や議論のまとめがニュースとして配信され、次の関心を生む。
- **MS-5.1** 区職員が公開ダッシュボードを担当課・注力分野で絞り込み、
  「検討中 → 採用 / 見送り」をシステム内の状態として理由付きで記録でき、当事者に通知される。
  採用を運用上の判断だけに留めず、循環が画面上で見える状態にする。
- **MS-5.2** 採用された施策がニュースとして配信され、元の課題カード・ダッシュボードへ
  リンクで戻れる。施策開始がダッシュボード上に注釈として残る。

### 区の目標との対応（S4、2026-10-24）

区の公開資料（[docs/sources/](sources/README.md)）から、区（Sponsor）の目標を Stakeholder `shibuya-city` の Need と
して probe-agent（System 7）に登録し、各 Objective がどの目標に寄与するかを結んだ。Need の文言は区の資料の要約で、
製品の解釈ではない。結び付けは 2 人チーム視点での判断（Claude が代行）。

| 区の目標（Need） | 根拠（資料・頁） | 寄与する Objective |
| --- | --- | --- |
| city-resident-voice: 区民が主体的に区政に関与し、より多くの声が反映されるまちづくり（次期計画案では共創型の都市運営） | 基本構想 p11、次期計画 策定方針・骨子（案）p14 | OBJ-1, OBJ-5 |
| city-diverse-opinions-in-planning: 在勤者・来街者を含む多様な人々の意見を計画に反映 | 策定方針・骨子（案）p5 | OBJ-5 |
| city-evidence-based-policy: EBPM で施策を立案・評価し改善を続ける | 策定方針・骨子（案）p5, p11 | OBJ-3, OBJ-4 |
| city-clear-to-residents: 政策と支援を区民に分かりやすく示す | 策定方針・骨子（案）p5、主要課題まとめ p3 | OBJ-3, OBJ-5 |
| city-childrearing-connected: 地域や社会とのつながりの中で安心して子育てできるまち | 政策の目的（案）p11、基本構想 p4 | OBJ-2 |
| city-isolated-families（問題）: 相談できる人がいない・地域との関係が希薄な子育て家庭がある | 主要課題まとめ p3、長期基本計画2017-2026 p26 | OBJ-2、OBJ-1（**仮説**: ニュース経由で相談につながらない家庭に届くかは未検証） |
| city-outdoor-play: 子どもが安心して外遊びできる環境 | 区民アンケート p7（43.9% で最多）、長期基本計画2017-2026 p27 | なし（製品の目標ではなく課題カードの題材） |

- 次期長期基本計画（2027-2036）の根拠は検討委員会の案で、素案は未公表。確定版が出たら S9 で見直す。
- 代表シナリオは 2026-10-24 に「授乳・おむつ替えスポット」から「近所で外遊びできる場所」に変えた（§6）。
  前者は読んだ区の資料に言及がなく、後者は区民アンケートで子育て支援の要望の最多（43.9%）で、区の計画にも
  遊び場の整備とプレーパークの成果指標がある。これに伴い city-outdoor-play は代表シナリオの題材になる
  （製品の Objective ではない点は変わらない）。

### 渋谷区 7 つの注力分野（課題カードの分類軸）

出典: 渋谷区基本構想（2016）p3 の未来像、p4〜10 の分野別基本構想（[要約](sources/shibuya-basic-concept-2016.md)）。

| ID | 注力分野 |
| --- | --- |
| AREA-1 | それぞれの成長を、一生よろこべる街へ（子育て・教育・生涯学習） |
| AREA-2 | あらゆる人が、自分らしく生きられる街へ（福祉） |
| AREA-3 | 思わず身体を動かしたくなる街へ（健康・スポーツ） |
| AREA-4 | 人のつながりと意識が未来を守る街へ（防災・安全・環境・エネルギー） |
| AREA-5 | 愛せる場所と仲間を、誰もがもてる街へ（空間とコミュニティのデザイン） |
| AREA-6 | あらたな文化を生みつづける街へ（文化・エンタテイメント） |
| AREA-7 | ビジネスの冒険に満ちた街へ（産業振興） |

## 6. 代表シナリオ

> 子どもが自由に安心して外遊びできる場所が、家の近くに足りないと感じたことはありませんか？

題材の根拠: 区民アンケート（2025）で子育て支援の今後充実すべき取組の最多が「子どもが自由に安心して外遊びが
できる環境づくり」（43.9%、[要約](sources/shibuya-survey-2025.md)）。長期基本計画2017-2026 も遊び場の確保・
整備を基本目標に置き、プレーパークの数を成果指標にしている（[要約](sources/shibuya-ltp-2017-2026.md)）。
2026-10-24 に「授乳・おむつ替えスポット」から変更した（[経緯](vision-sourcing.md#9-代表シナリオの変更2026-10-24)）。

1. 子育て中の保護者が、区の公園・子育て関連のニュース（公園の再整備、プレーパークのお知らせなど）を読み、
   近所にボール遊びや泥遊びができる場所が少ないことを AI に話す。
2. AI が関心を整理し、コミュニティ「子育て@渋谷」へ誘導する。
3. スレッドで保護者・区職員・AI が議論し、AI が課題候補
   「家から歩いて行ける範囲に、子どもが自由に遊べる場所が少ない地域がある」を提示する。
4. 課題カード「近所で外遊びできる場所が足りない」を作成。注力分野は AREA-1（関連: AREA-5 の公園を核とした
   地域コミュニティ）。KPI は次の 3 つ。
   - 地域別の公園・児童遊園地の数（区の公園一覧オープンデータで数えられる。現在 123 件）
   - プレーパークの数（区の長期基本計画の成果指標。現在 2 か所）
   - 外遊びの環境への満足度（参加者アンケート、5 段階）
   根拠は区民アンケートの結果と区の計画。公園一覧には広さ・ボール遊びの可否の列がないため、
   その部分は参加者の現場観測（F-11）で補う。
5. オープンデータ・アンケート・現場観測でデータを集め、KPI 追跡ダッシュボードを公開する。
6. 区の担当課（公園・子育ての所管課）がダッシュボードをピックアップし、施策を小さく検証する
   （例: 校庭開放の時間帯の拡大、公園の一角での外遊びイベント）。施策開始がダッシュボードへ注釈され、
   施策がニュースとして配信される。

## 7. 製品原則

probe-agent の設計原則を、市民参加の文脈に適用する。

- **P-1 当事者起点:** ダッシュボードの企画は行政内部ではなく、課題の当事者から始まる。
- **P-2 AI は伴走、決めるのは人:** AI は対話・整理・候補提示・データ整形を担う。課題カードの
  保存、ダッシュボードの公開、施策への採用は人の明示的な操作として記録する。
- **P-3 根拠に戻れる:** 課題・KPI・グラフは、元の発言・ニュース・データ出典へ遡れる。
  事実・意見・仮説・不明を区別して表示する。
- **P-4 未計測を成果に見せない:** データがない・取得できない・未集計を「0」や「問題なし」として
  表示しない。KPI の達成や施策の効果を AI が断定しない。
- **P-5 わかりやすさ:** 一般の区民がスマートフォンで迷わず使える。専門用語・複雑なグラフを
  前提にしない。
- **P-6 プライバシーと安全:** 個人を特定できる情報を公開ダッシュボードに出さない。
  個人の投稿・位置情報・アンケート回答は集計・匿名化してから可視化する。
- **P-7 量産できる:** 一つ一つを作り込むのではなく、同じ型（課題カード → KPI → ダッシュボード）で
  誰でも繰り返し作れることを優先する。

## 8. 非目標

- 行政の意思決定を AI や投票数で自動化すること（人気投票の多数決で施策を決める仕組みではない）
- 既存の SHIBUYA CITY DASHBOARD を置き換えること、またはそれとデータ連携・埋め込み連携すること。
  本システムは独立して公開する補完であり、公開ダッシュボードの固定 URL と CSV エクスポートで
  参照可能にする。既存側へ取り込むかは区の判断とする
- 個人への苦情対応・行政手続の窓口になること
- 根拠のない意見をデータとして可視化すること

## 9. probe-agent との関係

本プロジェクトは [probe-agent](https://github.com/dx-junkyard/probe-agent) の仕組みで実現する。

- **開発の進め方として:** probe-agent が対象 repository の `README.md` と `docs/**` を読み、
  Vision → Objective / Milestone → UX Journey / Requirement → Feature → 実装 → 評価証拠の
  lineage として整理する。本書・[UX](ux.md)・[Feature](features.md) の ID はその接続点である。
  probe-agent は committed files のみを読むため、文書の更新はコミットして初めて反映される。
- **製品の仕組みとして:** probe-agent が持つ「画面文脈を持つ AI 対話」「会話から型付き変更候補を
  作り人がレビューして保存する」「Gap を起点に仮説を調査へ送る」「候補を隔離して比較評価する」
  といった仕組みは、本製品の「AI との対話 → 課題カード → 仮説検証 → 採用」の流れと同じ形をしている。
  対応関係は [Feature §5](features.md#5-probe-agent-の仕組みとの対応) に記す。
