# 渋谷共創ダッシュボード Feature

**文書の役割:** UX を実現する機能（Feature）の正本
**上流:** [Vision](vision.md) → [UX](ux.md)

各 Feature（`F-*`）は、実現する UX Requirement（`UXR-*`）と Objective（`OBJ-*`）を参照する。
優先度は次の 3 段階とする。

- **MVP:** 代表シナリオ（授乳・おむつ替え）を通しで成立させるのに必要
- **Next:** 量産と行政採用のサイクルを継続的に回すのに必要
- **Later:** 規模拡大・高度化

## 2. Feature 詳細

### F-01 ニュース集約・配信

- 渋谷区ホームページ・各課の発信を取り込み、カテゴリ（子育て・観光・移動・安全 等）と
  注力分野（AREA-1〜7）で分類して一覧表示する。
- 記事ごとに出典 URL・担当課（「組織情報一覧」に基づく）・掲載日を保持する。
- 取り込みは定期実行。カテゴリ分類は AI が提案し、区の公式カテゴリがある場合はそれを優先する。

**受入条件:** カテゴリ絞り込みができ、すべての記事から出典ページへ到達できる。

### F-02 記事文脈つき AI 対話（雑談 Agent）

- 記事詳細から「AI と話す」で、記事を文脈として持つ対話スレッドを開始する。
- AI は利用者の関心を聞き出し、発言を「困りごと（事実・経験）」「意見」「疑問」「AI の推測」に
  分けて整理する。整理は会話の横に控えめに示し、会話を遮らない。
- 対話履歴はスレッドとして保存し、後から再開できる。整理結果は課題カード作成（F-06）へ渡せる。

**受入条件:** 3 往復の自由な対話の後、保存や分類を強制されずに終了・再開できる。
質問や仮定の発言が「事実」として整理されない。

### F-03 関心からのコミュニティ・課題推薦

- F-02 で整理された関心に基づき、関連するコミュニティと既存の課題カードを推薦する。
- 推薦理由（どの発言・どの注力分野が一致したか）を表示する。
- 既存の課題カードへの「共感」「補足」を可能にし、同じ課題の重複作成を減らす。

**受入条件:** 推薦から一操作でコミュニティ参加・課題カード閲覧に進める。

### F-04 コミュニティ・スレッド

- コミュニティ（名称・説明・メンバー数・Hot トピック）の作成と参加。
- スレッドの作成・返信。発言者の立場（住民・来訪者・事業者・区職員・AI）を表示する。
- コミュニティ内に「スレッド」と「課題カード」のタブを持つ。

**受入条件:** 区職員の発言が立場付きで表示され、一般参加者と区別できる。

### F-05 スレッド要約・課題候補提示（Community 形成支援 Agent）

- スレッドを要約し、課題候補（例:「安心拠点のスポット設置数が不足」）を根拠発言へのリンク付きで提示する。
- 新しいコミュニティ形成が有効な関心の集まりを検出し、作成を提案する。
- 課題候補から「課題カードを作る」で F-06 へ文脈を引き継ぐ。

**受入条件:** 課題候補のすべてに根拠発言へのリンクがあり、人が採用するまで課題カードは作られない。

### F-06 課題カード作成（課題カード作成 Agent）

- 項目: タイトル、対象者、場所・時間帯、根拠（ニュース・観測・データ）、注力分野、KPI（最大 3 つ）、
  起点（記事・スレッド・対話）、作成者、公開範囲、状態。
- 入口（記事・スレッド・対話）の文脈から AI が下書きを作り、人が編集して保存する。
  AI の下書きと人の入力を区別して記録する。
- 状態: 下書き → 公開 → 検証中 → ダッシュボード公開 → 区で検討中 → 採用 / 見送り。

**受入条件:** 3 つの入口すべてから、手作業の転記なしで下書きが作られる。保存は人の操作でのみ行われる。

### F-07 注力分野判定・KPI 提案

- 課題が渋谷区の 7 つの注力分野（AREA-1〜7）に寄与するかを判定し、理由を示す。
- KPI 候補を提示し、利用者が最大 3 件まで選ぶ。KPI 候補には測定方法とデータの入手見込み
  （オープンデータあり / アンケートが必要 / 不明）を添える。
- KPI はテンプレート（例: 設置数、日別平均利用件数、満足度 5 段階、段差箇所件数）として蓄積し、
  他の課題カードで再利用できるようにする。

**受入条件:** 判定結果に理由が付き、KPI は最大 3 件まで選択できる。いずれの分野にも寄与しない場合は理由を示す。

### F-08 オープンデータ検索（OpenData 検索 Agent）

- KPI ごとに、渋谷区・東京都・国のオープンデータカタログや公開情報（例: とうきょう子育てスイッチ）
  から関連データを検索する。
- 結果に出典・更新日・粒度（地域・時間）・ライセンス・形式を表示する。
- 見つからない場合は「見つからなかった」と検索範囲を示し、アンケート（F-11）を提案する。

**受入条件:** 提示されたすべてのデータに出典とライセンスがある。検索失敗を「データなし」と表示しない。

### F-09 データ整形支援（Data 整形支援 Agent / OpenData Bridge）

- PDF・Excel・CSV・Web ページなどの公開データを、KPI 用の時系列・地域別データへ変換する。
- 2023 年度 都知事杯 Open Data Hackathon ファイナリスト作品「OpenData Bridge」の整形機能を組み込む。
- 整形の手順（取り込み範囲・変換・集計）を利用者に示し、確認後に確定する（F-21 の AI 提案として扱う）。
- **MVP の範囲:** CSV / Excel 形式のオープンデータを KPI 用の時系列へ変換する整形に限定する。
  PDF・Web ページからの抽出と、区の新規公開データの自動整形は Next とする。

**受入条件:** 整形前後のサンプルと変換手順を確認でき、確定前のデータはダッシュボードに出ない。

### F-10 KPI 追跡ダッシュボード生成・公開

- 課題カードの KPI ごとに、目標値・現在値・推移グラフ・直近の傾向を持つカードを生成する。
- データソース（F-08 / F-09 / F-11）と更新頻度を KPI ごとに設定する。
- 公開は人の明示操作。公開されたダッシュボードは課題カードとコミュニティから辿れる。
- 公開すると固定の公開 URL（読み取り専用・OGP 付き）が発行され、KPI データを出典・ライセンス・
  更新日付きの CSV でエクスポートできる。書き込み・連携用の公開 API は Later。
- データ未取得・更新失敗・更新遅れを、KPI カード上で 0 や空のグラフと区別して表示する。

**受入条件:** 代表シナリオの 3 KPI（スポット設置数・日別平均利用件数・満足度）が目標値・現在値付きで表示される。

### F-11 アンケート・現場観測の収集

- KPI からアンケート（設問・選択肢・対象）を AI が下書きし、人が確認して配布する。
- コミュニティ参加者による現場観測（例: スポットの所在・混雑）の投稿を受け付ける。
- 回答は集計・匿名化してから KPI に反映する。回答数・収集期間を表示する。

**受入条件:** 個別回答はダッシュボードに表示されず、集計値と回答数だけが表示される。

### F-12 注釈と施策前後比較（課題解決支援 Agent）

- ダッシュボードのグラフに注釈（施策開始・イベント・データ定義変更）を追加できる。
- 注釈の前後で KPI を比較表示する。AI は変化の可能性のある要因を「仮説」として提示し、効果を断定しない。
- 次に試す小さな施策（PoC）の案を、根拠付きで提案する。

**受入条件:** 比較表示に「因果関係は未確認」である旨が示され、AI の仮説が事実として表示されない。

### F-13 区職員ビュー（選定・採用判断）

- 公開ダッシュボードを担当課（「組織情報一覧」）・注力分野・地域・参加者数・KPI 推移で絞り込み・比較する。
- 判断を「検討中 → 採用 / 見送り」のシステム内の状態として、理由・担当課付きで記録する。
  課題カードの状態に反映し、課題の当事者とコミュニティへ通知する。
- 職員としてスレッドへ公式に参加できる（F-04 / F-19）。

**受入条件:** 判断の記録に理由と判断者（担当課）が必ず残り、当事者に通知される。

### F-14 施策ニュース化と還流

- 採用された施策や議論の「まとめ」を、ニュース記事として下書き・配信する（区職員が確認して配信）。
- 施策ニュースは元の課題カード・ダッシュボードへリンクし、ダッシュボードに施策開始の注釈（F-12）を付ける。

**受入条件:** 施策ニュースから元の課題カードへ、課題カードから施策ニュースへ相互に到達できる。

### F-15 マイページ・進捗追跡・通知

- 自分の発言・課題カード・ダッシュボードと、それぞれの進捗段階を一覧表示する。
- 区の判断・施策開始・KPI の目標到達を通知する。

**受入条件:** 通知から該当画面へ一操作で移動できる。

### F-16 根拠・出典トレース（横断）

- 課題カード・KPI・グラフ・AI の提案すべてに、根拠（発言・記事・データセット・整形手順）への参照を持たせる。
- 表示上「事実（出典あり）」「意見（発言者）」「AI の推測」「未確認」を区別する。

### F-17 公開範囲・個人情報保護（横断）

- 公開範囲（自分だけ・コミュニティ・全体公開）を投稿・課題カード・ダッシュボードごとに持つ。
- 公開前に個人を特定し得る情報（氏名・住所・顔写真・詳細な位置）を検出して警告する。
- AI へ送る文脈から不要な個人情報を除去する。

### F-18 AI 障害時の手動フォールバック（横断）

- AI が応答しない・失敗した場合、入力済みの内容を保持し、再試行と手入力の両方を選べる。
- AI が失敗したことを隠して、成功したように見せない。

### F-19 アカウント・立場（ロール）（横断）

- ロール: 一般参加者・コミュニティ運営者・区職員（担当課付き）・管理者。
  住民・来訪者・事業者は一般参加者の属性として登録時に選び、発言・課題カードに表示する。
- 区職員ロールは区が認証・付与する。発言・判断の表示に立場を反映する。

### F-20 アクセシビリティ・モバイル対応（横断）

- 390px 幅で主要導線を横スクロールなしに完了できる。下部タブナビゲーション。
- キーボード操作・スクリーンリーダー対応。状態を色だけで表さない。

### F-21 AI 提案の共通パターン（横断）

- AI が作るもの（課題候補・課題カード下書き・注力分野判定・KPI 候補・整形手順・グラフ案・アンケート案・
  施策仮説）を、共通の「AI 提案」エンティティとして保存する。
- 状態は「提案中 → 採用 / 編集して採用 / 却下」の有限集合。採用されたときだけ正式なエンティティを作る。
- 記録: 提案者（AI とモデル名）、根拠参照、判断者、判断日時、判断方法（人の明示操作）。
- UI は共通部品（「AI の提案」ラベル、根拠リンク、3つの操作）を使う。

**受入条件:** AI 提案を採用せずに正式なエンティティが作られる経路が存在しない。

### F-22 データ提供者への利用状況の公開（Later）

- データセットごとに、利用している課題カード・ダッシュボードの件数と一覧を公開し、
  オープンデータ提供者（STK-6）へ整備の優先度を返す。

## 3. AI Agent 群と Feature の対応

構想資料の AI Agent 群を、Feature の担い手として位置づける。どの Agent も「候補を作る」までを担い、
保存・公開・採用は人が行う。

| Agent | 担う Feature | 入力 | 出力（すべて候補） |
| --- | --- | --- | --- |
| 雑談 Agent | F-02, F-03 | 記事、利用者の発言 | 関心の整理、推薦 |
| Community 形成支援 Agent | F-05 | スレッドの発言 | 要約、課題候補、コミュニティ作成提案 |
| 課題カード作成 Agent | F-06, F-07 | 記事・スレッド・対話の文脈 | 課題カード下書き、注力分野判定、KPI 候補（最大 3） |
| OpenData 検索 Agent | F-08 | KPI | データセット候補（出典・ライセンス付き） |
| Data 整形支援 Agent（OpenData Bridge） | F-09, F-01 | 公開データ、区の新規公開データ | 整形手順と整形済みデータ |
| 課題解決支援 Agent | F-11, F-12 | KPI 推移、注釈、議論 | アンケート案、施策仮説、PoC 案 |

## 4. 主要データ（エンティティ）

```text
News ──(起点)──▶ Conversation ──(整理)──▶ InterestSummary
  │                                         │
  ▼                                         ▼
Community ──▶ Thread ──▶ Post ──(根拠)──▶ IssueCard ──▶ KPI (≤3) ──▶ DataSource
                                            │             │           (OpenData / Survey / Observation)
                                            │             ▼
                                            │         Dashboard ──▶ Annotation
                                            ▼             │
                                        FocusArea (AREA-1〜7)
                                                          ▼
                                     AdoptionDecision (区の担当課) ──▶ PolicyNews ──▶ News
```

- すべてのエンティティは作成者（人 / AI）・作成日時・根拠参照を持つ。
- AI が作った候補（AIProposal）は、人が採用するまで正式なエンティティにならない。
- 変更は履歴として残し、過去の判断の根拠を再現できるようにする。

## 5. probe-agent の仕組みとの対応

本製品の機能は、probe-agent の既存の仕組みと同じ形をしている。実装時はこれらの設計契約・
実装を参照・流用候補とする（流用可否は実装前に個別に確認する）。

| 本製品の Feature | probe-agent の仕組み | 共通する形 |
| --- | --- | --- |
| F-02 記事文脈つき AI 対話 | Assistant Discussion（画面コンテキスト AI）、関心起点の Interview 対話 | 対象の文脈を保持した会話スレッド。会話は正本を書き換えない |
| F-05 / F-06 課題候補 → 課題カード | 会話結論の Proposal 化とレビュー、form prefill | AI は型付き候補を作り、人が項目を選んで保存する |
| F-06 / F-07 課題・注力分野・KPI | Purpose Chain、Product Objective / Milestone / Gap | 課題 = 現状と目標状態の差（Gap）、KPI = 検証可能な到達点 |
| STK-* / 価値交換 | Stakeholder Value Network | 立場ごとの Need と価値のやりとり |
| F-11 / F-12 仮説検証・施策前後比較 | 共同検討 UX（Gap → 仮説 → 調査 → 還流）、Experiment | 仮説を競合説明・反証条件付きで扱い、結果を断定しない |
| F-13 区の採用判断 | 人間ゲート（`decision_method: manual`） | 採用・公開・達成の確定は人の明示判断 |
| F-16 根拠トレース | provenance / evidence / revision | 事実・推論・仮説・不明の区別と出典への遡及 |
| F-17 個人情報保護 | Secret Redaction | 取り込み・永続化・表示・LLM の各境界での除去 |
| F-18 AI 障害時 | heuristic fallback 禁止・fail closed | 失敗を成功に見せず、保持した成果と再開手段を示す |

また開発プロセスとして、本書の Feature ID を probe-agent の Feature Map / Feature-to-Code
mapping の接続点とし、実装後は代表シナリオ（[UX §5](ux.md#5-代表シナリオでの検証)）を
評価証拠として Objective / Milestone へ還流する。

## 6. MVP の範囲

代表フロー「ニュース → AI 対話 → 課題カード → KPI 追跡ダッシュボード公開 → 区職員の採用判断」
（[UX §5](ux.md#5-代表シナリオでの検証)）を、授乳・おむつ替えシナリオで通しで成立させる最小構成。
[UX §5](ux.md#5-代表シナリオでの検証) の検証の順番に合わせて段階的に作る。
