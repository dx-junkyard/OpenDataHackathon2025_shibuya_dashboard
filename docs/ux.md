# 渋谷共創ダッシュボード UX

**文書の役割:** Vision を実現する利用体験（Journey / Step / Requirement）の正本
**上流:** [Vision](vision.md)
**下流:** [Feature](features.md)

この文書は「誰が、どの場面で、どんな体験をすれば Vision に近づくか」を定める。
Journey（`J-*`）は Stakeholder（`STK-*`）と Objective（`OBJ-*`）を参照し、
各 Journey Step で満たすべき要件を UX Requirement（`UXR-*`）として定義する。
UXR を実現する機能は [Feature](features.md) が所有する。

---

## 1. UX 原則

| ID | 原則 | 具体的な意味 |
| --- | --- | --- |
| UXP-1 | 読むことから始まる | 最初に入力フォームや分類を求めない。ニュースを読み、気軽に話すところから始まる |
| UXP-2 | 次の一操作が分かる | 各画面に主操作は一つ。「次に何をすれば課題がダッシュボードに近づくか」を常に示す |
| UXP-3 | 段階的に詳しくする | 最初は結論・現在地・次の操作。根拠、データ出典、議論の履歴は必要なときに開く |
| UXP-4 | 根拠と不確かさが見える | 事実（出典あり）・意見（誰の発言か）・AI の推測・未確認を見分けられる。データ未取得を 0 と見せない |
| UXP-5 | AI は提案、人が決める | AI の課題候補・KPI 候補・グラフ案は「候補」として表示し、保存・公開・採用は人のボタン操作で行う |
| UXP-6 | スマホで完結 | 390px 幅で主要操作を横スクロールなしに完了できる。下部タブで主要領域を行き来する |
| UXP-7 | 誰にでも分かる | 専門用語を避け、グラフは目標値・現在値・傾向を一目で示す。色だけで状態を表さない |
| UXP-8 | 循環が見える | 自分の声が課題 → ダッシュボード → 施策 → ニュースへ進んだことを、本人が追える |

## 2. 画面構成（情報アーキテクチャ）

構想資料のモックアップに基づくモバイルファーストの構成。下部タブで 6 領域を切り替える。

| タブ | 役割 | 主に使う Journey | 主な Feature |
| --- | --- | --- | --- |
| ニュース | 区のローカルニュース・施策ニュースをカテゴリ（子育て・観光・移動・安全 等）で閲覧。記事から AI 対話・課題カード作成へ | J-1, J-6 | F-01, F-02, F-03, F-14 |
| コミュ | 参加中コミュニティのスレッドと課題カード。スレッド作成、課題作成 | J-2, J-3 | F-04, F-05 |
| コミュ参加 | 関心カテゴリ・注力分野・地域でコミュニティを検索・一覧して参加する。推薦（F-03）からは該当コミュニティの詳細へ遷移する。合うコミュニティが無ければ新規作成を提案する | J-1, J-2 | F-03, F-04 |
| 課題 | 課題カードの一覧・詳細。注力分野・KPI・根拠・状態 | J-3, J-4 | F-06, F-07, F-08, F-11 |
| ダッシュ | KPI 追跡ダッシュボード（目標値・現在値・傾向・注釈）。公開 URL・CSV エクスポート | J-4, J-5 | F-09, F-10, F-12 |
| マイ | 自分の発言・課題・ダッシュボードとその後の進捗、通知 | J-6 | F-15 |

区職員ロールには、公開ダッシュボードの比較と採用判断を行う「職員ビュー」が追加される（J-5, F-13）。

### AI 提案の共通パターン

AI が作るものはすべて、どの画面でも同じ「AI 提案」として扱う（UXR-X1）。

```text
提案中 ──▶ 採用 / 編集して採用 ──▶ 正式なエンティティ（課題カード・KPI・整形済みデータ 等）
   └────▶ 却下
```

- 表示部品: 「AI の提案」ラベル、根拠へのリンク、採用・編集して採用・却下の3操作
- 記録: 提案者（AI / モデル）、判断者、判断日時、判断方法（人の明示操作）
- 画面ごとに配置は違ってよいが、部品・状態の語彙・記録は共通にする

## 3. Journey

### J-1 ニュースから関心に気づく（住民・来訪者・事業者）

**Stakeholder:** STK-1, STK-2, STK-3 ／ **Objective:** OBJ-1

| Step | 体験 | UX Requirement |
| --- | --- | --- |
| 1-1 | ニュースタブで区のニュースをカテゴリ別に読む | UXR-1 ニュースをカテゴリで絞り込め、記事の出典（区 HP・担当課）が分かる |
| 1-2 | 記事を読んで思ったことを AI に気軽に話す | UXR-2 記事の文脈を保ったまま AI と自由に対話できる。分類や入力項目を先に求めない |
| 1-3 | AI が話を整理し、困りごと・関心を言葉にしてくれる | UXR-3 AI は利用者の発言・記事の事実・AI の推測を区別して整理を返す。話すだけで終えてもよい |
| 1-4 | 同じ関心のコミュニティや既存の課題カードを紹介される | UXR-4 関連コミュニティ・課題カードを理由付きで提示し、参加・閲覧へ一操作で進める |

**完了状態:** 関心が言葉になり、コミュニティへ参加した、または既存の課題カードに共感・補足した。

### J-2 コミュニティで議論し課題を深掘りする（住民・コミュニティ・区職員）

**Stakeholder:** STK-1, STK-4, STK-5 ／ **Objective:** OBJ-2

| Step | 体験 | UX Requirement |
| --- | --- | --- |
| 2-1 | コミュニティ（例: 子育て@渋谷）に参加し、話題のスレッドを見る | UXR-5 コミュニティの規模・話題（Hot）・関連課題カードが一目で分かる |
| 2-2 | スレッドで経験や意見を投稿する。区職員も情報提供を求めて参加する | UXR-6 発言者の立場（保護者・区職員・AI 等）が表示され、区職員の公式な発言と区別できる |
| 2-3 | AI がスレッドを要約し、課題候補を提示する | UXR-7 AI の課題候補は根拠となる発言へのリンク付きで「候補」として表示され、議論を遮らない |
| 2-4 | 課題候補から課題カード作成へ進む | UXR-8 スレッドの文脈（発言・根拠）を引き継いで課題カードを作成でき、手作業の転記が不要 |

**完了状態:** スレッドの議論から、根拠付きの課題候補が生まれ、課題カード作成に進んだ。

### J-3 課題カードを作る（住民・コミュニティ）

**Stakeholder:** STK-1, STK-2, STK-3, STK-4 ／ **Objective:** OBJ-3

| Step | 体験 | UX Requirement |
| --- | --- | --- |
| 3-1 | ニュース記事・スレッド・AI 対話のいずれからでも「課題カードを作る」 | UXR-9 どの入口からでも、起点の文脈がタイトル・根拠の下書きとして補われる |
| 3-2 | タイトル・対象者・場所/時間帯・根拠を確認・編集する | UXR-10 AI の下書きと人の入力が区別され、すべて編集できる。根拠には出典（ニュース・観測・データ）を付けられる |
| 3-3 | AI が 7 つの注力分野への寄与を判定し、KPI 候補を提案する | UXR-11 注力分野の判定理由と KPI 候補を表示し、利用者がタップで KPI を最大 3 件まで選ぶ。寄与しない場合は理由を示す |
| 3-4 | 保存してコミュニティに公開する | UXR-12 保存は人の明示操作。保存後は課題タブ・コミュニティに表示され、起点の会話・記事へ戻れる |

**完了状態:** 注力分野と KPI（最大 3 つ）を持つ課題カードが、根拠付きで公開された。

### J-4 仮説を検証しダッシュボードにする（住民・コミュニティ・事業者）

**Stakeholder:** STK-1, STK-3, STK-4, STK-6 ／ **Objective:** OBJ-4

| Step | 体験 | UX Requirement |
| --- | --- | --- |
| 4-1 | 課題カードの KPI ごとに、使えるデータを探す | UXR-13 KPI に関連するオープンデータを AI が検索し、出典・更新日・粒度・ライセンスを添えて提示する |
| 4-2 | データが足りない KPI はアンケートや現場観測で集める | UXR-14 KPI からアンケートを作成・配布し、回答を集計できる。収集中・未収集の状態が分かる |
| 4-3 | 集めたデータを KPI 用に整形する | UXR-15 データ整形（形式変換・集計・地域や時間での切り出し）を AI が支援し、整形内容を利用者が確認できる |
| 4-4 | KPI ごとに目標値を決め、ダッシュボードを作って公開する | UXR-16 KPI カードは目標値・現在値・推移・直近の傾向を示す。データ未取得は「未取得」と表示する。公開は人の明示操作。公開すると固定の公開 URL が発行され、KPI データを出典付き CSV でダウンロードできる |
| 4-5 | 小さな施策を試し、施策開始などを注釈として記録する | UXR-17 グラフに注釈（施策開始・イベント等）を追加でき、施策前後の変化を見比べられる。効果を AI が断定しない |

**完了状態:** KPI 追跡ダッシュボードが公開され、データが継続的に更新されている。

### J-5 区職員がダッシュボードを採用し施策に反映する（区職員）

**Stakeholder:** STK-5 ／ **Objective:** OBJ-5

| Step | 体験 | UX Requirement |
| --- | --- | --- |
| 5-1 | 公開ダッシュボードを担当課・注力分野・地域で絞り込んで閲覧する | UXR-18 区の組織情報（担当課）と注力分野で整理された一覧から、根拠・参加者数・KPI 推移を比較できる |
| 5-2 | 気になる課題のコミュニティに参加し、状況を確認・情報提供する | UXR-19 区職員として課題・スレッドに参加し、公式な情報提供や質問ができる |
| 5-3 | ダッシュボードをピックアップし、施策検討の状態を記録する | UXR-20 「検討中 → 採用 / 見送り」をシステム内の状態として理由・担当課付きで記録でき、課題カードの状態に反映され、当事者とコミュニティに通知される |
| 5-4 | 施策や議論のまとめをニュースとして配信する | UXR-21 施策ニュースは元の課題カード・ダッシュボードへリンクし、ダッシュボードに施策開始の注釈が付く |

**完了状態:** 区民発のダッシュボードが施策検討に使われ、その結果がニュースとして区民に戻った。

### J-6 自分の声のその後を見る（住民・来訪者・事業者）

**Stakeholder:** STK-1, STK-2, STK-3 ／ **Objective:** OBJ-5

| Step | 体験 | UX Requirement |
| --- | --- | --- |
| 6-1 | マイページで自分が関わった発言・課題・ダッシュボードを見る | UXR-22 自分の関わりが、課題 → ダッシュボード → 施策のどこまで進んだかを段階で示す |
| 6-2 | 区の判断や施策ニュースの通知を受け取る | UXR-23 区の判断・施策開始・KPI の目標到達を通知し、該当画面へ一操作で移動できる |

**完了状態:** 参加者が、自分の声が施策につながった（またはまだ途中である）ことを理解している。

## 4. 横断 UX Requirement

| ID | 要件 |
| --- | --- |
| UXR-X1 | AI の出力（要約・課題候補・KPI 候補・データ整形・グラフ案）には「AI の提案」と明示し、根拠へ戻るリンクを付ける |
| UXR-X2 | AI が使えない・遅いときも、入力済みの内容を失わず、人が手入力で課題カードやダッシュボードを作れる |
| UXR-X3 | 公開範囲（自分だけ・コミュニティ・全体公開）を常に表示し、公開前に個人情報の含有を警告する |
| UXR-X4 | キーボード・スクリーンリーダーで主要導線を完走でき、状態を色だけで示さない |
| UXR-X5 | データの取得失敗・未取得・更新遅れを、データ不存在や 0 と区別して表示する |

## 5. 代表シナリオでの検証

[Vision §6](vision.md#6-代表シナリオ) の外遊びシナリオ（2026-10-24 に授乳・おむつ替えから変更）を、通し導線の受入シナリオとする。

**代表フロー:** ニュース → AI 対話 → 課題カード → KPI 追跡ダッシュボード公開 → 区職員の採用判断と当事者への通知
（J-1 → J-3 → J-4 → J-5 の最小部分）。スレッド起点（J-2）、施策ニュース化と注釈（J-5 の残り）、
マイページ（J-6）は代表フローの次の段階とする。

**検証の順番:**

1. J-3 の入口: ニュース記事と AI 対話の文脈から課題カードの下書きが作られ、人が編集・保存するまで
   （AI 提案の共通パターンもここで最初に検証する）
2. J-3 → J-4: KPI からデータを用意し、ダッシュボードを公開するまで
3. J-1 の推薦と J-5 の採用判断を接続し、循環を閉じる

次を実測して評価する（未実測を成功として扱わない）。

- ニュース閲覧から課題カード保存までの画面遷移数と所要時間
- 起点の文脈（記事・発言・根拠）を手作業で転記した回数（目標 0 回）
- AI の提案と人の入力・事実と推測を、利用者が正しく見分けられたか
- 区職員役が、ダッシュボードから根拠と議論の経緯を説明できたか

### 次の手順（S7〜S8）で扱う差の候補

- 公園一覧に広さ・遊べる内容がなく、課題カードの KPI の一部を公開データで測れない（現場観測 F-11 で補えるか）。
- 現状の A3・A4（声が束ねられない、結果が見えない）は仮説のまま。区の担当課への聞き取りで確かめる。
- デモのデータが旧シナリオのまま（C-3）。→ 2026-10-24 に外遊びのデータへ切り替える。
